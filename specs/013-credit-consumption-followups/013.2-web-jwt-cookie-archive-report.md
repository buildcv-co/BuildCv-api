## Summary

The web JWT-in-cookie flow closes the auth gap between NextAuth.js (Web session management) and the .NET backend (Bearer JWT). End-to-end browser flows now work without mocked auth, and every BFF route that calls a protected backend endpoint uses a unified `getJwtFromSession()` bridge.

**Chained delivery strategy**: 3 chained PRs (`feature-branch-chain`), mirroring the 012-wompi + 013-credit-consumption pattern. Each PR kept build + test + format green; all work merged directly to `main` with conventional commits and work-unit grouping. ~150 / ~250 / ~80 line budgets per PR kept review scope manageable.

**Key architectural choice (Option B)**: the owner approved **NextAuth.js** over the cookie-only Option A. Justified by battle-tested CSRF/session rotation/secure cookies, ~200 LoC saved vs. custom implementation, and future-proof multi-provider support (Apple, Microsoft, GitHub one-line additions). Documented as a **ratified Art. VI amendment**; the constitution bump 1.1.0 → 1.2.0 is the only outstanding paperwork.

## Art. VI Amendment (Ratified)

Adding `next-auth@^4.24.7` as new dependency required owner ratification per Constitution §Gobernanza → Proceso de enmienda. **RATIFIED** based on:

- **Robustness**: CSRF, session rotation, secure cookies built-in (battle-tested, audited by thousands of projects)
- **Completeness**: Industry-standard OAuth/session library; eliminates ~200 LoC of custom security code
- **Constitution compliance**: Art. VI "No sobre-ingeniería" — cost of +1 dep justified by value
- **Future scalability**: Adding more OAuth providers (Apple, Microsoft, GitHub) is one-line in NextAuth config

**Pending follow-up**: Constitution bump 1.1.0 → 1.2.0 (single-file PR to `.specify/memory/constitution.md` to formally ratify the dep + v0.5/v1 persistence boundary). **Recommended as a follow-up PR but NOT a blocker for this archive.**

## Risks & Known Limitations

1. **Art. III + Art. VII WARNINGs** (pre-existing from `009-auth`) — should be addressed via the v1.2.0 constitution bump alongside the next-auth amendment.
2. **Constitution bump pending** — 1.2.0 should be executed as a single-file follow-up PR.
3. **E2E uses `encode()` workaround** — real OAuth PKCE flow cannot be intercepted by Playwright; documented as acceptable (same approach used in 012-wompi and 013-credit-consumption E2E suites).
4. **Shared secret distribution** — `NEXTAUTH_SECRET` must match `JwtSettings:Secret` byte-for-byte; needs runbook for production deploy (Render env var sync + rotation procedure).
5. **Cache cleanup uses `setInterval` with `unref()`** — graceful during shutdown but not deterministic; acceptable because cache TTL is bounded.
6. **NextAuth v4 lock-in** — tight coupling to NextAuth's callback pattern. Mitigation: NextAuth is stable, v4 has been the standard for 4+ years, v5 maintains similar API.

## Migration Notes

- No DB migration needed (auth uses existing tables from 009-auth)
- New env vars required: `NEXTAUTH_SECRET`, `NEXTAUTH_URL`, `GOOGLE_CLIENT_ID/SECRET`, `LINKEDIN_CLIENT_ID/SECRET`, `JWT_CACHE_TTL_SECONDS`
- Production deploy must set these via Render env vars (already configured in `render.yaml`)
- Critical: `NEXTAUTH_SECRET` MUST equal `JwtSettings:Secret` byte-for-byte (HS256 RFC requirement, ≥32 chars); fail-fast startup check validates this in `Program.cs`
