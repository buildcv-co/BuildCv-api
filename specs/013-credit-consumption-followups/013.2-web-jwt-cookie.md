# 013.2 — Web JWT-in-Cookie End-to-End

## Status
[Spec] — Pendiente de design

## Overview

Completar el flujo de autenticación entre NextAuth.js (Web) y el backend .NET. Hoy el BFF del frontend pasa cookies pero el backend no las lee para los endpoints de créditos en contexto browser. El resultado: los flujos E2E funcionan en tests (con auth mockeada) pero NO en producción (usuarios reales).

## Problem

1. User hace sign-in con Google/LinkedIn → NextAuth.js crea session cookie
2. User navega a `/analizar` → click "Adaptar CV" → se llama ruta BFF
3. Ruta BFF necesita llamar backend `POST /api/v1/adapt`
4. Backend requiere `Authorization: Bearer {jwt}`
5. BFF tiene la session cookie pero NO un JWT
6. Backend responde 401 (no JWT) → adapt falla en browser

## Goal

El usuario puede hacer sign-in vía OAuth y usar la app end-to-end sin manejo manual de JWT ni mocks.

## Requirements

### R1: Endpoint sesión-a-JWT

**Given** una NextAuth session cookie existe
**When** se llama `GET /api/v1/auth/session` desde el Web BFF
**Then** la respuesta es HTTP 200 con `{ jwt, expiresAt, user: { id, email, name } }`
**And** el JWT está firmado con el mismo secret que el resto de la API
**And** el JWT contiene claims: `sub` (userId), `email`, `name`, `exp`, `iat`

### R2: BFF middleware

**Given** la ruta BFF `/api/credits/balance` es llamada
**When** la request tiene una NextAuth session cookie válida
**Then** el middleware lee la sesión, genera JWT, y agrega `Authorization: Bearer {jwt}` a la request al backend
**And** el backend responde 200 con el balance
**And** el BFF devuelve la misma response al cliente

**Given** la NextAuth session cookie falta o expiró
**When** la ruta BFF es llamada
**Then** el BFF responde 401 `{ error: "AUTH/UNAUTHENTICATED" }`
**And** el backend NO es llamado

### R3: JWT caching

**Given** un JWT fue generado para una sesión en los últimos N minutos
**When** la misma sesión se usa para una nueva request
**Then** el JWT cacheado se reusa (no se re-firma)
**And** el JWT se invalida cuando la sesión expira
**And** el TTL del cache es 5 minutos (configurable vía `JWT_CACHE_TTL_SECONDS`)

### R4: E2E browser test

**Given** Playwright lanza un browser
**When** el test hace sign-in con Google OAuth (mockeado)
**And** navega a `/analizar`
**And** llama `/api/credits/balance`
**Then** la respuesta es 200 con el balance del usuario
**And** los logs del backend muestran que el JWT fue validado

## API contracts

### `GET /api/v1/auth/session` (NUEVO)

- **Auth**: requiere NextAuth session cookie (NO Bearer JWT)
- **Response 200**: `{ jwt: string, expiresAt: DateTime, user: { id, email, name } }`
- **Response 401**: `{ error: "AUTH/UNAUTHENTICATED" }`

## Frontend integration

### BFF middleware (NUEVO)

- `BuildCv-web/lib/api/jwt.ts` — `getJwtFromSession(session)`: lee NextAuth session, devuelve JWT cacheado
- `BuildCv-web/middleware.ts` (NUEVO o modificar): aplica a todas las rutas `/api/*`
- Cache in-memory con TTL (Map<sessionId, { jwt, expiresAt }>)

### Modificaciones a BFF existentes

- `BuildCv-web/app/api/credits/balance/route.ts` — usa `getJwtFromSession()` en vez de `session.accessToken`
- `BuildCv-web/app/api/credits/history/route.ts` — idem
- `BuildCv-web/app/api/payments/*/route.ts` — idem (ya tienen el gap)

## Out of scope

- Multi-device session sync (single-device solo para v1)
- JWT refresh tokens (NextAuth session refresh es suficiente)
- Rate limiting en `/api/v1/auth/session`
- Admin impersonation
- Session analytics o tracking

## Risks

1. **JWT signing secret consistency** — El BFF y backend deben usar el mismo secret. Riesgo bajo (config en env vars).
2. **Cache invalidation** — Si NextAuth invalida la sesión, el cache puede tener un JWT viejo hasta 5 min. Mitigación: check de expiración antes de usar.
3. **Playwright OAuth mock** — Necesita un mock realista del flow OAuth. Complejidad media.
