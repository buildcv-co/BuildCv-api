# 013.3 — Refund Mid-Stream Defense-in-Depth Test

## Status
[Spec] — Pendiente de apply

## Overview

Agregar test explícito que verifica que NO se emite refund cuando el stream del LLM falla DESPUÉS de emitir el primer token. Actualmente esto está enforced por arquitectura (la excepción `AI_UNAVAILABLE` triggerea el refund antes de que el stream empiece), pero falta un test explícito que prevenga regresión.

## Background

En 013-credit-consumption R3 (Refund on LLM failure), el comportamiento es:
- Si LLM falla ANTES del primer token → refund emitido
- Si LLM falla DESPUÉS del primer token → NO refund (trabajo fue realizado)

Esto está enforced por `RefundConsumptionHandler` siendo llamado solo en `AI_UNAVAILABLE` (pre-stream), no en fallos parciales del stream. Pero no hay test que pruebe este contrato.

## Problem

Si alguien refactorea el adapt flow y accidentalmente mueve el refund call al stream-failure handler, los usuarios recibirían refunds por trabajo parcial (injusto para el negocio). No hay test que catches esto.

## Goal

Agregar test explícito que lockea el contrato: refund solo para pre-stream failures.

## Requirements

### R1: Mid-stream failure sin refund

**Given** un usuario llamó `POST /api/adapt` con 1 crédito consumido
**And** el stream del LLM emitió ≥1 token
**When** el stream falla mid-way (ej. upstream timeout)
**Then** la respuesta es HTTP 502 con output parcial O HTTP 502 sin output
**And** NO se crea ledger entry de Refund
**And** el `CreditBalance` del usuario queda sin cambios después del fallo
**And** el ledger entry de Consumption del pre-adapt SIGUE presente

### R2: Pre-stream failure con refund (sanity check)

**Given** un usuario llamó `POST /api/adapt` con 1 crédito consumido
**And** la llamada al LLM falla ANTES de emitir cualquier token
**When** el fallo es detectado
**Then** se crea ledger entry de Refund con `Reason=Refund`, `Delta=+1`
**And** el `CreditBalance` del usuario se incrementa de vuelta al original
**And** la respuesta es HTTP 502 con `{ error: "ADAPT/UPSTREAM_FAILURE" }`

## Test scenarios

### Unit test: mid-stream sin refund

```csharp
[Fact]
public async Task MidStreamFailure_DoesNotIssueRefund()
{
    // Arrange: user con balance=1
    var ledger = new InMemoryCreditLedger();
    var userId = Guid.NewGuid();
    await ledger.AccreditAsync(userId, CreditLedgerReason.Welcome, "test", 1, null, ct);

    // Act: simular adapt que emite 1 token luego falla mid-stream
    var adaptSimulator = new AdaptSimulator(ledger);
    var result = await adaptSimulator.SimulateAdaptWithMidStreamFailure(userId, ct);

    // Assert
    Assert.Equal(0, (await ledger.GetBalanceAsync(userId, ct)).Balance);
    Assert.DoesNotContain(
        await ledger.GetHistoryAsync(userId, 10, null, ct),
        e => e.Reason == CreditLedgerReason.Refund);
    Assert.Single(
        await ledger.GetHistoryAsync(userId, 10, null, ct),
        e => e.Reason == CreditLedgerReason.Consumption);
}
```

### Unit test: pre-stream con refund

```csharp
[Fact]
public async Task PreStreamFailure_IssuesRefund()
{
    // Arrange: user con balance=1
    var ledger = new InMemoryCreditLedger();
    var userId = Guid.NewGuid();
    await ledger.AccreditAsync(userId, CreditLedgerReason.Welcome, "test", 1, null, ct);

    // Act: simular adapt que falla antes de emitir tokens
    var adaptSimulator = new AdaptSimulator(ledger);
    var result = await adaptSimulator.SimulateAdaptWithPreStreamFailure(userId, ct);

    // Assert
    Assert.Equal(1, (await ledger.GetBalanceAsync(userId, ct)).Balance);
    Assert.Single(
        await ledger.GetHistoryAsync(userId, 10, null, ct),
        e => e.Reason == CreditLedgerReason.Refund);
}
```
